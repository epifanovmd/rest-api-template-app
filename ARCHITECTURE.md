# Architecture Guide

Документ описывает архитектурную модель сервера: композиционный корень, модульную
систему, слои внутри модуля, границы между модулями, жизненный цикл приложения, модель
доступа, событийную модель, фоновые задачи, хранилище файлов и способ работы с
данными. Он не описывает конкретные доменные модули, сущности, эндпоинты и события —
это область кода и проектной памяти.

- Выбор места для нового кода — [MODULE-CHEATSHEET.md](MODULE-CHEATSHEET.md).
- Правила написания и оформления кода — [CONVENTIONS.md](CONVENTIONS.md).
- Принципы проектирования — [CLEAN-CODE.md](CLEAN-CODE.md), [DESIGN-PRINCIPLES.md](DESIGN-PRINCIPLES.md).

Технологические решения (HTTP-фреймворк, генератор маршрутов, DI-контейнер, ORM,
транспорт реального времени, валидатор, очередь задач, хранилище) описываются здесь
категориями, а не брендами: архитектура не должна зависеть от конкретной библиотеки.
Актуальный выбор фиксируется в README проекта.

## Модульный монолит

Сервер — модульный монолит: одна кодовая база, одна база данных, один образ, но код
разбит на изолированные модули с явными границами. Модуль — единица владения: он
владеет своими таблицами, бизнес-правилами, HTTP-контрактом, событиями, ошибками,
правами и фоновыми задачами. Один и тот же код запускается в разных ролях процесса
(см. «Роли процесса»).

```
src/
  main.ts            ← точка входа: инструментирование, запуск, graceful shutdown, фатальные ошибки
  app.ts             ← жизненный цикл приложения (composition root)
  app.module.ts      ← корневой модуль: список всех модулей приложения
  app.container.ts   ← единственный экземпляр IoC-контейнера
  config.ts          ← валидированная конфигурация окружения
  core/              ← ядро: DI, модули, auth, ошибки, события, контракты задач и хранилища, наблюдаемость
  common/            ← универсальные хелперы без знания о домене и инфраструктуре
  middleware/        ← сквозные HTTP-middleware и порядок их регистрации
  routing/           ← сгенерированные маршруты, спецификация, системные маршруты
  migrations/        ← миграции схемы БД
  types/             ← глобальные типы и declaration augmentation
  test/              ← общая тестовая инфраструктура (фабрики моков)
  modules/           ← доменные и инфраструктурные модули
    <feature>/       ← один модуль = одна предметная область или одна инфраструктурная подсистема
test/e2e/            ← интеграционный набор против настоящего сервера
```

| Область      | Ответственность                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------- |
| `core`       | механика, на которой стоят все модули: DI, модули, auth, ошибки, события, контракты, реестры      |
| `common`     | чистые вспомогательные функции, пригодные в любом проекте                                         |
| `middleware` | обработка каждого HTTP-запроса до маршрутизации                                                   |
| `routing`    | связывание контроллеров с HTTP-сервером; код здесь генерируется                                   |
| `modules`    | бизнес-логика и инфраструктурные подсистемы (очередь, хранилище, сокеты), каждая — в своём модуле |

`core`, `common` и `types` не знают о `modules` — это проверяет архитектурный тест.
`modules` не знают о `routing` и `middleware`. `app` знает обо всём и только собирает.

## Жизненный цикл приложения

Порядок запуска фиксирован и ориентирован на работу под оркестратором:

0. **Инструментирование** — отправка ошибок подключается первым импортом точки
   входа, до загрузки остальных модулей.
1. **HTTP-сервер и системные маршруты** поднимаются первыми — liveness-проба отвечает
   сразу, даже если остальное ещё не готово.
2. **База данных** — подключение с бесконечным retry и экспоненциальной задержкой.
   Сервер не падает без БД: он ждёт и отдаёт readiness = 503.
3. **Миграции** — применяются при старте под блокировкой БД либо отдельным шагом
   развёртывания. В режиме «миграции отдельным шагом» отставшая схема — ошибка запуска.
4. **Модули и DI** — загрузчик обходит дерево модулей и регистрирует провайдеры.
5. **Маршруты приложения** — после модулей, потому что маршруты резолвят
   контроллеры и провайдеры маршрутов из контейнера. В роли воркера не регистрируются.
6. **Bootstrappers** — инициализация модулей (seed, запуск очереди задач, сокетов).
   Bootstrapper сам объявляет, критичен ли он: некритичный при ошибке пропускается с
   предупреждением, критичный — прерывает запуск.
7. **Готовность** — readiness-проба возвращает 200, пока бутстраперы завершены и БД
   доступна (фоновая проверка); потеря БД снимает реплику с трафика.

Остановка по сигналу: readiness = 503 → пауза, чтобы балансировщик снял реплику →
HTTP-сервер перестаёт принимать соединения и ждёт in-flight запросы (по таймауту
рвёт оставшиеся) → bootstrappers уничтожаются в обратном порядке с изоляцией ошибок
(активные задачи дорабатывают до своего таймаута, затем возвращаются в очередь) →
подписки EventBus снимаются → закрывается БД → накопленные ошибки отправляются. Сигналы обрабатываются один раз; при превышении общего таймаута процесс
завершается принудительно. Необработанное исключение переводит процесс в останов,
необработанный reject промиса — логируется и отправляется в трекер ошибок.

Системные маршруты (liveness, readiness, health, метрики) не принадлежат ни одному
модулю, не проходят через аутентификацию, CORS и лимит запросов.

### Роли процесса

Один образ и один код запускаются в одной из ролей (переменная окружения):

| Роль     | HTTP                   | Клиентские сокеты | Очередь задач                        |
| -------- | ---------------------- | ----------------- | ------------------------------------ |
| `api`    | API и системные пробы  | да                | только постановка                    |
| `worker` | только системные пробы | нет               | выполнение задач и расписаний        |
| `all`    | API и системные пробы  | да                | постановка и выполнение (разработка) |

Воркер не принимает клиентов реального времени, но его слушатели событий отправляют
клиентам через общий адаптер реального времени, поэтому событие, возникшее в задаче,
доходит до клиента, подключённого к любому API-процессу. Тяжёлые зависимости
(обработка медиа) нужны только образу воркера.

### Несколько реплик

Приложение рассчитано на горизонтальное масштабирование API за балансировщиком и
отдельные процессы-воркеры. Всё, что должно быть согласовано между процессами,
хранится вне процесса: лимиты запросов, присутствие пользователей, комнаты
real-time транспорта, отзыв токенов, кэши прав — в Redis; одноразовые секреты,
сессии и задачи — в БД. Периодическую задачу выполняет ровно один процесс кластера —
это гарантирует очередь задач, а не таймеры в процессе. Клиентский IP и протокол
берутся из заголовков прокси только при явно доверенном прокси.

Два общих механизма ядра для согласования процессов:

- **Сигналы между процессами** — LISTEN/NOTIFY основной БД: одно соединение на
  набор каналов модуля, переподключение после обрыва. Сигнал, отправленный в
  транзакции, доходит только после её фиксации. Без LISTEN (пулер в режиме
  транзакций, обрыв) подписчики переходят на опрос — механизм сообщает о своём
  состоянии. Модуль объявляет свои каналы, а не открывает своё соединение.
- **Живое состояние с TTL** (последние снимки, счётчики, отметки) — общее
  хранилище ядра поверх Redis с атомарными операциями; без Redis — память
  процесса, только для однопроцессного режима. Модуль работает в своём
  пространстве ключей.

## Базовая ветка и ветки-примеры

Главная ветка — платформа без предметной области: ядро, пользователи и доступ,
сессии, файлы, задачи, почта, реальное время. Предметные примеры живут в
ветках-примерах, каждая — главная ветка плюс модули примера и их миграции.

- Исправление общего кода делается в главной ветке и вливается в ветки-примеры;
  в ветке-примере правится только код её модулей.
- Модули главной ветки не импортируют модули примеров: связь — только через точки
  расширения. Поэтому пример подключается добавлением модулей, а не правкой базы.
- Схема главной ветки — её миграции; пример добавляет свои миграции поверх, не
  пересоздавая базовые.

## Модульная система и DI

Модуль — класс с декоратором, описывающим его состав:

```ts
@Module({
  imports: [OtherModule], // модули, чьи провайдеры нужны этому
  entities: [Feature], // сущности ORM этого модуля
  providers: [
    Repository,
    Service,
    Controller,
    asSocketListener(Listener),
    asJobHandler(FeatureJob),
  ],
  bootstrappers: [FeatureBootstrap], // опционально: задачи инициализации
})
export class FeatureModule {}
```

Правила регистрации:

- **Модули — единственный источник истины для контейнера.** Декоратор
  `@Injectable()` только помечает класс как пригодный для инъекции; регистрацию
  выполняет исключительно `providers` модуля.
- **Контроллеры регистрируются как провайдеры** — генератор маршрутов получает их из
  контейнера.
- **Репозитории** помечаются `@InjectableRepository(Entity)`: загрузчик модулей сам
  создаёт их поверх подключения к БД для указанной сущности.
- **Сущности** перечисляются в `entities` модуля-владельца. Подключение к БД
  собирает их из дерева модулей, без поиска файлов по маске; тест реестра падает,
  если сущность объявлена, но не зарегистрирована.
- **Провайдер по токену** (`{ provide: TOKEN, useClass }`, обычно через хелпер
  `asXxx(Cls)`) используется для multi-inject: несколько реализаций одного контракта
  собираются по символу. Это основной механизм расширения — см. «Точки расширения».
- **Абстрактный класс как токен** — для контракта с одной реализацией, выбираемой
  конфигурацией (очередь задач, хранилище файлов): потребитель инжектит абстракцию,
  инфраструктурный модуль привязывает реализацию.
- Все провайдеры — singleton. Повторная регистрация одного класса игнорируется.
- Корневой модуль перечисляет все модули приложения. Порядок важен только там, где
  один модуль собирает реализации из других по токену: такой модуль идёт последним.
- Зависимости приходят через конструктор. Прямое обращение к контейнеру допустимо
  только в composition root и в точках интеграции с фреймворком (аутентификация
  маршрутов, middleware генератора маршрутов), где инъекция невозможна.

## Точки расширения ядра

Ядро не импортирует модули. Модуль расширяет платформу, регистрируя реализацию
контракта под токеном-реестром; потребитель реестра о конкретных модулях не знает.

| Реестр                               | Что добавляет модуль                                       | Потребитель                 |
| ------------------------------------ | ---------------------------------------------------------- | --------------------------- |
| схемы аутентификации                 | новый способ аутентификации для декоратора безопасности    | аутентификация tsoa         |
| обработчики задач                    | очередь с политикой повторов, расписанием, видимостью      | очередь задач               |
| политики доступа к задачам           | кто, кроме владельца, видит и отменяет задачи своего scope | API задач                   |
| исполнитель внешних очередей         | выполнение очередей, объявленных внешними (агенты)         | очередь задач               |
| обработчики HTTP со своим протоколом | маршруты, читающие тело сами, до разбора тела и лимитов    | composition root            |
| провайдеры комнат                    | комнаты, в которые соединение входит само при подключении  | транспорт реального времени |
| политики комнат                      | право войти в комнату по запросу клиента                   | транспорт реального времени |
| провайдеры маршрутов                 | маршруты вне генератора (потоковая раздача файлов)         | composition root            |
| индикаторы здоровья                  | проверка своей зависимости в диагностике здоровья          | системные маршруты          |
| политики пароля                      | дополнительные правила пароля                              | модуль-владелец пароля      |
| пробы использования файла            | запрет удалить файл, на который ссылается домен            | модуль файлов               |
| реестр прав                          | права модуля (с областью — и `:own`); засев собирает все   | модуль ролей                |
| обработчики и слушатели событий      | входящие события клиента и доставка доменных событий       | транспорт реального времени |
| связи пользователей                  | кто кому «контакт» и кому видно присутствие                | модуль профиля              |

Контракты, которые модуль дополняет типами, а не реализацией, расширяются
дополнением интерфейса (declare module) в файле модуля-владельца: карта событий
реального времени, данные шаблонов писем. Общий файл контракта при добавлении или
удалении модуля не правится.

Новая точка расширения появляется как токен и интерфейс в модуле-потребителе (или в
ядре, если потребитель — ядро), а не как импорт конкретного модуля.

## Слои внутри модуля

```
HTTP-запрос / задача / событие клиента
   │
   ▼
Controller · JobHandler · SocketHandler  ← вход: контракт, security, валидация, контекст
   │
   ▼
Service      ← бизнес-правила, транзакции, доменные события, постановка задач, возвращает DTO
   │
   ▼
Repository   ← доступ к данным: запросы, выборки, без бизнес-правил
   │
   ▼
Entity       ← схема таблицы и связи
```

| Слой       | Знает о                                    | Не знает о                                      |
| ---------- | ------------------------------------------ | ----------------------------------------------- |
| Controller | Service, DTO, схемы валидации              | Repository, Entity, транспорт реального времени |
| JobHandler | Service, контекст задачи                   | HTTP, транспорт реального времени               |
| Service    | Repository, Entity, DTO, EventBus, очередь | HTTP-контекст, транспорт реального времени      |
| Repository | Entity, ORM                                | DTO, бизнес-правила, события                    |
| Listener   | EventBus, эмиттер реального времени, DTO   | HTTP, Repository (кроме чтения для адресации)   |

Ключевые границы:

- **Контроллер и обработчик задачи тонкие.** Они объявляют контракт и делегируют.
  Бизнес-условия, запросы к БД и формирование ответа в них запрещены.
- **Наружу уходит только DTO.** Сущность ORM никогда не возвращается из контроллера
  и не отдаётся в события: DTO — единственная форма данных на границе модуля.
- **Сервис не знает о транспорте.** Он публикует доменное событие; кто и куда его
  доставит — ответственность слушателей.
- **Репозиторий не принимает решений.** Он умеет искать и сохранять; проверка прав,
  статусов и инвариантов — в сервисе.
- **Валидация входа — на границе.** Схема валидации применяется декоратором на
  методе контроллера или обёрткой входящего события реального времени; сервис
  получает уже проверенные данные и проверяет только бизнес-инварианты.

## Границы между модулями

- Модуль экспортирует наружу только то, что объявлено в его корневом `index.ts`
  (public API). Импорт внутренних файлов чужого модуля запрещён.
- Внутри модуля — относительные пути; `core` и `common` импортируются через их
  публичные индексы.
- Прямая зависимость модуля от сервиса или репозитория другого модуля допустима, если
  это чтение или вызов в рамках одного запроса. Реакция на изменение в другом модуле
  всегда идёт через события, а не через прямой вызов «в обратную сторону».
- Циклические зависимости между модулями запрещены. Если два модуля нуждаются друг в
  друге — общее выносится в третий модуль, связь заменяется событием или токеном.
- Связи между сущностями разных модулей объявляются на уровне ORM (внешние ключи,
  каскады), а не поддерживаются кодом.
- Инфраструктурные модули (очередь, хранилище, транспорт реального времени, почта,
  файлы) не знают о доменных модулях: они предоставляют контракт и токен, а доменные
  модули регистрируют свои реализации.

## HTTP-слой

- **Маршруты генерируются** из декораторов контроллеров вместе с OpenAPI-спецификацией.
  Сгенерированный файл маршрутов и спецификация не редактируются вручную,
  пересобираются при каждом запуске в разработке и при сборке, коммитятся актуальными.
- **Версия API** — в пути: все маршруты модулей живут под `/api/v<N>/`. Несовместимое
  изменение контракта — новая версия, а не правка существующей.
- **Middleware** — сквозная обработка каждого запроса в фиксированном порядке:
  метрики → идентификатор запроса → логирование → перехват ошибок → системные
  маршруты → заголовки безопасности → CORS → ограничение частоты → разбор тела.
  Перехват ошибок стоит выше всех обработчиков, которые могут бросить.
- **Guards** — точечная защита конкретного маршрута (частота на эндпоинт, требование
  подтверждённого email, HTTPS, whitelist адресов). Guard объявляется декоратором на
  методе и не является заменой аутентификации.
- **Аутентификация** — реестр схем безопасности: по имени схемы из декоратора и списку
  scopes схема возвращает контекст вызывающего или отклоняет запрос. Контекст кладётся
  в запрос и извлекается в контроллере единственным хелпером.
- **Маршруты вне генератора** (потоковая раздача, подписанные загрузки) регистрирует
  модуль через провайдер маршрутов; они не попадают в спецификацию и описываются в
  README модуля.

### Контракт ошибок

Любой ответ со статусом ≥ 400 имеет одну форму: `status`, машинный `code`,
человекочитаемый `message`, необязательные `details` и `requestId`. Стек — только вне
production.

- **Код стабилен** — на него опирается клиент. Доменная ошибка имеет код
  `<ПРЕФИКС_МОДУЛЯ>_<КЛЮЧ>`, объявленный в модуле; ошибка без доменного кода получает
  код по статусу (`NOT_FOUND`, `CONFLICT`, `INTERNAL_ERROR`).
- **Валидация** — единообразно для генератора маршрутов и схем: 400
  `VALIDATION_ERROR`, `details` — «поле → сообщение».
- **Статусы:** нет прав — 403, не найдено или скрыто — 404, конфликт с текущим
  состоянием (дубликат, недопустимый переход, объект используется) — 409, лимит —
  429 с `Retry-After`, недоступная зависимость — 503.
- **5xx** — обобщённое сообщение наружу, подробный лог и отправка в трекер ошибок;
  внутренний текст и SQL не утекают. Ошибка формата значения в БД — 400.
- Контракт ошибки объявлен на каждом контроллере как ответ по умолчанию и попадает в
  спецификацию. Сообщения — на языке пользователя API.

### Пагинация

- **Список** с известным общим числом — страница по смещению: `items`, `total`,
  `offset`, `limit`. Лимит нормализуется единым хелпером и ограничен сверху; список
  без лимита запрещён.
- **Лента**, в которую записи добавляются во время чтения, — страница по курсору:
  `items` и непрозрачный `nextCursor` (`null` — конец). Курсор строится по
  монотонному ключу с тай-брейком по идентификатору.
- Собственные формы списков не вводятся.

## Аутентификация и доступ

Модель доступа — роли плюс права (RBAC + permissions), у прав над сущностями с
владельцем — область «все / свои»:

- Токен доступа привязан к серверной сессии и несёт `scope` (доступ, обновление,
  второй фактор), идентификаторы пользователя и сессии, роли и **эффективные права** —
  объединение прав ролей и прямых прав, вычисленное при выдаче. Проверка права на
  запросе не обращается к БД. Токен одного назначения не принимается вместо другого.
- **Отзыв:** завершение сессии мгновенно делает её access-токены недействительными —
  проверка идёт по списку отзыва во внешнем хранилище с коротким локальным кэшем, а не
  по сроку жизни токена.
- **Refresh** ротируется при каждом обновлении, в БД хранится только его хеш;
  повторное использование старого refresh считается кражей и завершает сессию.
  Веб-клиенты могут получать refresh в httpOnly-cookie. Смена пароля или привилегий
  завершает сессии пользователя — через событие, а не прямым вызовом.
- **Защита входа:** блокировка аккаунта после серии неудачных попыток, политика
  пароля (длина, частые пароли, совпадение с идентификаторами), хеширование пароля
  медленной функцией. События безопасности записываются в журнал аудита.
- Право — строка формата `домен:действие`. Иерархия wildcard: `*` покрывает всё,
  `домен:*` — все действия домена. Суперпользователь — отдельная роль либо право `*`.
  Ядро знает только эти два значения; остальные роли и права принадлежат модулям.
- **Область права — «все / свои».** У права на действие над сущностями с владельцем
  есть пара `<право>:own` — то же действие только над своими сущностями (где
  пользователь владелец или создатель). Право на все и покрывающий его wildcard
  включают `:own`, обратное неверно; последний сегмент `own` зарезервирован за
  областью. Область вычисляет ядро — по контексту запроса или по идентификатору
  пользователя (политики комнат и слушатели, где запроса нет).
- Модуль объявляет свои права в реестре прав; право с областью объявляется флагом, и
  пару `:own` реестр регистрирует сам. Засев ролей собирает права без общего списка,
  каталог прав отдаёт клиенту и вариант «только свои». Роли и права хранятся в БД как
  строки и расширяются без деплоя.
- Права ролей по умолчанию перечисляются в базовом модуле строками — он не зависит от
  доменных модулей; что каждое такое право объявлено в реестре, проверяет тест.
- В декораторе безопасности указываются права (`permission:<домен>:<действие>`), а
  не роли. Маршрут над сущностями с владельцем требует как минимум своё
  (`permission:<домен>:<действие>:own` — его проходит и право на все), а сервис
  сужает доступ по области общим помощником ядра: проверка конкретной сущности и
  ограничение выборки «все / только свои». Проверка «владелец или суперпользователь»
  вручную не пишется.
- Сущность вне области пользователя скрыта — 404; видимая, но без права на
  действие — 403. Дочерние сущности доступны только в видимом родителе. Список
  ограничен областью и принимает необязательный фильтр «только мои».
- Смена смысла существующих прав — миграция данных, сохраняющая текущий доступ ролей,
  пользователей с прямыми правами и API-ключей.
- **Вызывающие разных видов:** пользователь, бот, сервис по API-ключу. Каждый вид —
  своя схема аутентификации в реестре; ключ сервиса несёт свои scopes и действует от
  имени выпустившего пользователя.
- Альтернативные способы входа (второй фактор, биометрия, passkeys) завершаются
  созданием той же серверной сессии и выдачей тех же токенов.
- Соединение реального времени аутентифицируется тем же access-токеном. Истечение
  токена сообщается клиенту заранее, клиент обновляет токен в том же соединении; без
  обновления соединение рвётся после короткой паузы. Завершённая сессия рвёт свои
  соединения.

## Данные

- Сущность ORM описывает таблицу: имя таблицы во множественном числе, класс — в
  единственном, колонки — snake_case в БД и camelCase в коде. Nullable-колонка в
  типах — `| null`, а не `undefined`.
- Индексы, уникальные ограничения, каскадные удаления и обнуления объявляются в
  сущности. Целостность данных — обязанность БД, а не кода.
- Схема меняется только миграциями, автосинхронизации нет ни в одном окружении.
  Миграция генерируется из изменений сущностей, проверяется глазами и добавляется в
  явный упорядоченный список миграций. Пока проект не выпущен, схема может быть
  собрана в одну начальную миграцию; после выпуска каждое изменение — новая миграция.
  CI проверяет, что миграции применяются на чистую БД и что сущности не разошлись со
  схемой.
- Несколько записей в одной операции изменяются в транзакции. Внутри транзакции
  используются репозитории менеджера транзакции, а не инжектированные.
- Фоновая задача, порождённая изменением данных, ставится в ту же транзакцию
  (outbox): откат отменяет и задачу.
- События публикуются **после** фиксации транзакции. Слушатель никогда не должен
  увидеть незакоммиченное состояние.
- Гонки решаются в БД: атомарный условный `UPDATE` с проверкой числа затронутых
  строк для переходов состояния, идемпотентная вставка для засева, блокировка строки
  для операций, которые не должны идти параллельно. Нарушение уникальности — 409.
- Одноразовые секреты (токены сброса, приглашения, ключи) хранятся хешем; сам
  секрет показывается один раз.
- Секреты, которые приложению нужно вернуть в исходном виде (ключи интеграций,
  приватные ключи, пароли для выдачи клиенту), хранятся зашифрованными ключом
  приложения (аутентифицированное шифрование). Ключ — в конфигурации, не в БД;
  в ответы API и логи секрет не попадает без явной необходимости.
- Данные, у которых важна история (сообщения, аудит), удаляются мягко — флагом и
  очисткой содержимого; справочные данные — жёстко, с каскадами на уровне БД.
- Бинарные данные в БД не хранятся: в таблице — ключ объекта хранилища и метаданные.

## Ошибки

- Бизнес-ошибка — исключение из единого семейства HTTP-исключений; доменные ошибки
  модуля объявляются одним вызовом с префиксом и превращаются в коды автоматически.
  Сервис бросает, middleware превращает в ответ; контроллер не ловит и не
  переупаковывает.
- Ошибка обрабатывается один раз на подходящем уровне: репозиторий не ловит,
  сервис ловит только чтобы перебросить осмысленнее, middleware — конечная точка.
- Ошибка задачи несёт машинный код и признак «повторять ли»: неповторяемая ошибка
  завершает задачу сразу, любая другая — повтор по политике очереди.
- Обработчики событий реального времени и слушатели EventBus изолируют свои ошибки:
  сбой одного обработчика не роняет соединение и не мешает остальным. Клиент
  получает тот же машинный код, что и в HTTP.
- Отсутствие сущности, которая обязана существовать, проверяется явной проверкой с
  выбросом исключения, а не оператором `!`.

## События и реальное время

Событийная модель — единственный способ, которым модули реагируют друг на друга:

```
Service ──emit──▶ EventBus ──▶ Listener ──▶ эмиттер реального времени ──▶ клиент
                        └────▶ Listener другого модуля (побочный эффект: задача, аудит)
```

- Событие — класс с неизменяемыми полями (readonly). Ключ подписки — сам класс, а не
  строковое имя: это безопасно при сборке и даёт типизацию.
- Синхронная публикация — fire-and-forget с изоляцией ошибок обработчиков.
  Асинхронная — параллельное ожидание всех обработчиков без прерывания на первой
  ошибке. Выбор определяется тем, нужно ли сервису дождаться побочных эффектов.
- EventBus — внутрипроцессный. Надёжный побочный эффект, который должен пережить
  сбой (письмо, push, вебхук, обработка файла), слушатель не выполняет сам, а ставит
  задачей в очередь.
- **Обработчик соединения** (клиент → сервер) регистрируется по токену и подписывает
  входящие события только через валидирующую обёртку: схема входа, лимит частоты на
  соединение и событие, ответ-подтверждение с машинным кодом ошибки.
- **Слушатель событий** (EventBus → клиент) отправляет данные только через
  сервис-эмиттер: адресно пользователю (все его устройства), в комнату или всем.
  Эмиттер работает через общий адаптер — событие доходит до соединений на любом
  процессе.
- **Комнаты:** личная комната пользователя — при подключении; комнаты доменных
  сущностей — через провайдеров комнат (восстанавливаются при переподключении) или
  по запросу клиента с проверкой политикой комнаты. Запрос на вход в комнату
  принимается сразу после установки соединения, до регистрации присутствия:
  клиент подписывается в момент подключения и переподключения.
- **Сущности с владельцем:** в комнату списка входит только держатель права
  просмотра на все; пользователь с областью «свои» получает изменения лично, если он
  владелец или создатель сущности. Когда сущность перестаёт быть своей (сменился
  владелец), бывшему владельцу отправляется её снятие, а его комнаты пересматриваются.
- События не буферизуются: пропущенное за время обрыва клиент восстанавливает,
  перечитав состояние после переподключения.
- Карты событий клиент → сервер и сервер → клиент типизированы. Модуль транспорта
  объявляет только события соединения; каждый модуль дополняет карты своими
  событиями в своём файле. Новое событие сначала добавляется в карту, затем
  используется.
- Инфраструктура реального времени запускается bootstrapper-ом после всех модулей и
  при остановке снимает свои записи присутствия.

## Задачи и воркеры

Фоновая работа — только через очередь задач на основной БД. Задачи переживают
рестарт, выполняются с повторами на процессах-воркерах (или воркерами агентов — для
внешних очередей), а их постановка может быть атомарна с изменением данных.

- **Обработчик** реализует контракт обработчика и регистрируется в реестре. Его
  описание задаёт очередь (`домен.действие`), число повторов, задержку и
  экспоненциальный рост, срок выполнения, параллельность, расписание, видимость и
  признак внешнего выполнения. Политика применяется к очереди при каждом старте.
- **Постановка** — через абстракцию очереди: отложенный запуск, дедупликация по
  ключу, приоритет, транзакция (outbox).
- **Запрос-ответ** поверх очереди: поставить задачу и дождаться её итога с
  таймаутом — для синхронного вызова исполнителя из запроса. Итог приходит сигналом
  БД о завершении (с опросом как страховкой); таймаут снимает задачу, ошибка
  исполнителя возвращается вызывающему с его кодом.
- **Периодические задачи** объявляются расписанием в описании обработчика и
  выполняются ровно одним процессом кластера; расписание, удалённое из кода,
  снимается. Таймеры в процессе и ручные блокировки для периодической работы не
  используются.
- **Видимые задачи** хранят статус, прогресс, хвост лога, результат и ошибку, имеют
  владельца и область видимости (scope). Отмена работает между процессами: ждущая
  задача отменяется сразу, выполняющаяся получает сигнал отмены. Изменения
  публикуются событием и доходят до клиента по сокету. Кто, кроме владельца, видит и
  отменяет задачи scope, решает политика доступа модуля-владельца scope.
- **Аренда:** выполняющаяся задача продлевает аренду; задача с истёкшей арендой
  (упавший процесс) возвращается в очередь или падает окончательно. У внешней задачи
  аренды нет — её ход приходит событиями исполнителя, а не дольше срока выполнения
  она падает. Номер попытки — барьер: итог устаревшей попытки не принимается.
- **Хранение:** завершённые записи задач удаляются периодической задачей по сроку
  хранения из конфигурации.
- **Корреляция:** каждая задача выполняется с собственным идентификатором запроса,
  попадающим во все её логи и метрики.
- **Внешние задачи** (очереди, объявленные внешними) выполняет исполнитель внешних
  очередей (токен ядра) — **воркеры агентов**, см. «Агенты». Очередь задач лишь
  передаёт ему задачу и отражает ход и итог, которые исполнитель сообщает, в своей
  записи: передача — сразу после коммита постановки (сигнал в транзакции outbox), если
  подходящий исполнитель на связи, а задача очереди — для повторов передачи и ожидания
  исполнителя; дважды задачу не передаёт условный захват записи. Файлы задачи —
  подписанные ссылки хранилища по ключам, которые выводит хук очереди; результат
  переносится в домен хуком очереди в одной транзакции с завершением задачи. Записи
  меняются условно: повтор сообщения исполнителя ничего не задваивает.

## Агенты

Агент — программа на узле (сервер, VM, контейнер), связанная с бэкендом; агент и SDK —
отдельный продукт ([github.com/epifanovmd/agent](https://github.com/epifanovmd/agent)),
формат сообщений задаёт его спецификация ([sdk/spec](https://github.com/epifanovmd/agent/blob/main/sdk/spec/README.md)).
Бэкенд не реализует протокол сам: сторону сервера ведёт серверный SDK, подключённый
модулем агентов к платформе. Агент ничего не знает о предметной области: он передаёт
запросы, настройки, события и метрики воркеров, не разбирая их.

- **Связь** открывает только агент: WebSocket на том же HTTP-сервере, что API и
  транспорт реального времени. Маршруты агента обслуживаются до разбора тела и лимитов
  (свой протокол).
- **Воркеры** — HTTP-сервисы на unix-сокете на любом языке, без SDK; что запускать на
  узле, решают настройки узла. Воркер описывает себя манифестом (ключи настроек со
  схемой значения, маршруты, события); без него агент воркер не регистрирует. Бэкенд
  выбирает воркер по манифесту, а не по имени узла.
- **Сервер хранит желаемые настройки воркеров** (версия по ключу только растёт) и
  присылает их после каждого подключения; значение проверяется по схеме из манифеста до
  отправки. Агент хранит настройки и важные сообщения (события воркеров, итоги) на диске
  до подтверждения и работает без связи.
- **Хранилище SDK** — реализация его контракта поверх БД проекта: записи агентов
  целиком с условной записью по версии одним запросом, настройки — строкой на ключ со
  счётчиком версии. Несколько процессов API работают с одним хранилищем без затирания.
- **История** (события воркеров, метрики, итоги действий) — не забота SDK: модуль
  агентов пишет её из событий SDK в свои таблицы и журнал аудита; событие подтверждается
  агенту после записи, повтор доставки отсекается по id сообщения.
- **Несколько процессов:** агент подключён к одному процессу. Изменения в хранилище
  доходят до процесса с соединением сигналом через БД. Вызов, которому нужно
  соединение (запрос к воркеру, задача, действие, наблюдение), из другого процесса SDK
  пересылает в процесс с соединением по внутреннему HTTP-маршруту (вне публичного API,
  закрыт общим секретом процессов; адрес процесса — его имя в сессии агента); без
  пересылки такой вызов отклоняется с просьбой повторить. Процесс-воркер — без связи с
  агентами: читает записи и задаёт настройки через общее хранилище, вызовы — пересылкой.
- **Задачи проекта:** очереди, объявленные внешними, исполняют воркеры агентов через
  токен ядра — модуль задач о модуле агентов не знает. Очередь называет тип задачи
  воркера (стандарт задач спецификации: быстрая — итог в ответе, долгая — ход и итог
  событиями, состояние и отмена — запросами); исполнитель выбирает агента, чей воркер
  объявил тип в манифесте; после переподключения агента состояние сверяется опросом.
- **Замена занятого воркера** (перезапуск, обновление) откладывается до окончания его
  работы: API отвечает сразу, итог приходит событием действия в реальное время.
- **Наблюдение:** статус воркеров, метрики узла и воркеров, журнал, события и проблемы
  — события SDK → шина событий → комнаты реального времени. Пока клиент смотрит агента,
  сервер просит агента присылать метрики чаще и журнал подробнее и снимает просьбу, когда
  клиент уходит.
- **Идентичность:** токен регистрации (выпущенный, в том числе многоразовый для парка
  машин, или общий токен окружения) обменивается на учётные данные агента; в БД —
  хеш секрета. Отзыв закрывает сессию; изменяющие действия выполняются от имени
  пользователя и попадают в журнал аудита. Метки токена и его автор приходят
  событием регистрации — по нему предметный модуль связывает агента со своей
  сущностью.
- **Доступ:** права модуля агентов дают доступ ко всем агентам; предметный модуль
  может открыть доступ к «своим» агентам политикой (токен-реестр модуля агентов) —
  например, владельцу сущности, к которой привязан агент.
- **Обновление:** сборки агента и воркеров из выпуска подписываются ключом выпуска (вне
  бэкенда), бэкенд раздаёт каталог выпуска; замена занятого воркера ждёт окончания его
  работы; в контейнере обновление — новым образом.

## Хранилище файлов

- Модули работают с абстракцией хранилища по **ключам**; раскладку ключей определяет
  модуль-владелец, пути и адреса хранилища наружу не выходят. Драйверы — локальный
  диск (разработка, один хост) и S3-совместимое хранилище; выбор — конфигурацией.
- Клиент получает только **подписанные ссылки** с ограниченным сроком: для диска —
  подпись приложения и маршрут раздачи с поддержкой диапазонов и кэширования, для
  S3 — presigned-ссылки самого хранилища с публичным адресом, отличным от
  внутреннего. Подпись асинхронна, поэтому DTO с файлами собираются из заранее
  подписанной пачкой карты ссылок; синхронной подписи в DTO нет.
- **Загрузка:** небольшие файлы — multipart через API с проверкой расширения, типа и
  сигнатуры; крупные — напрямую в хранилище по подписанной ссылке на запись с точным
  размером и типом, затем подтверждение, которое проверяет объект и запускает
  обработку.
- **Обработка медиа** (конвертация, превью, метаданные) — фоновой задачей на
  воркере; до её завершения файл доступен в исходном виде. Незавершённые загрузки
  удаляются периодической задачей.
- Удаление файла, на который ссылается домен, запрещено (409) — модули сообщают об
  использовании через пробу.

## Конфигурация

- Переменные окружения читаются из файла по имени окружения и валидируются схемой при
  старте. Невалидная конфигурация — немедленное падение с понятной ошибкой, а не
  сюрприз в рантайме. Небезопасная production-конфигурация (пустой пароль БД, CORS
  `*`, нет Redis, неполные ключи хранилища) — ошибка запуска.
- Код получает конфигурацию из типизированного объекта, а не из `process.env`.
  Общие настройки платформы — в едином конфиге; настройки модуля — схема рядом с
  модулем через общий хелпер (те же правила разбора и падения при старте). Модуль
  подключается и удаляется вместе со своими настройками.
- Секреты не попадают в репозиторий; шаблон файла окружения с описанием переменных —
  попадает.
- Флаги окружения (`isProduction`, `isDevelopment`) — единственный способ ветвить
  поведение по среде; строковые сравнения по месту запрещены.
- Необязательные интеграции (почта, push, трекер ошибок) выключаются
  пустой переменной. Отсутствие обязательной для операции интеграции в production —
  503, вне production — безопасная заглушка (например, письмо в лог).

## Наблюдаемость

- **Логи** — структурированный логгер, единый на приложение; `console.*` не
  используется. Чувствительные поля редактируются на уровне логгера. Идентификатор
  запроса (или задачи) попадает в каждую запись через асинхронный контекст, без
  передачи логгера по цепочке. 5xx логируются с контекстом, 4xx — нет.
- **Метрики** — в формате Prometheus на системном маршруте, с необязательной защитой
  токеном: HTTP (метка маршрута — шаблон, не URL), ошибки по машинному коду, задачи
  по очередям, соединения реального времени, метрики процесса. Воркер отдаёт свои
  метрики тем же маршрутом.
- **Ошибки** — 5xx и фатальные ошибки процесса уходят в трекер ошибок, если он
  настроен.
- **Здоровье:** liveness — процесс жив; readiness — бутстраперы завершены и БД
  доступна; health — живые проверки БД, Redis и индикаторов модулей с таймаутом.

## Сборка и запуск

- Сборка — компилятор TypeScript, без шагов копирования. Всё, что код читает в
  рантайме, либо импортируется (JSON-спецификация), либо лежит в каталоге ассетов
  вне исходников (шаблоны писем по локалям) и находится по пути от корня проекта —
  одинаково в разработке, сборке и контейнере.
- Сборка сохраняет имена классов: ORM, DI и EventBus используют классы как ключи.
  Минификация с искажением имён запрещена.
- Тесты исключаются из production-сборки.
- Запуск без явного окружения — production с безопасными умолчаниями.
- **Образ** один, с двумя целями сборки: API — без тяжёлых системных зависимостей,
  воркер — с ними. Многостадийная сборка, непривилегированный пользователь,
  init-процесс как PID 1, файловая система только для чтения.
- **Развёртывание:** образ собирается и публикуется в registry по тегу релиза; на
  сервере образ только скачивается. Порядок: одноразовый шаг миграций → API
  (масштабируемый) и воркер. Приложение само схему не меняет (миграции при старте
  выключены). Инфраструктура (БД, Redis, S3-совместимое хранилище с созданием bucket)
  — в том же описании развёртывания и заменяется внешними сервисами конфигурацией.
- Для разработки — отдельное описание инфраструктуры: БД, Redis, тестовый SMTP и
  S3-совместимое хранилище.

## Автоматические проверки

Архитектурные правила должны быть машинно проверяемыми там, где это возможно:

| Область             | Что проверяется                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Маршруты и контракт | генерация проходит, спецификация и маршруты закоммичены актуальными                                               |
| Границы ядра        | ядро и глобальные типы не импортируют модули (архитектурный тест)                                                 |
| Сущности            | каждая сущность зарегистрирована в модуле                                                                         |
| Импорты             | порядок и группировка импортов и экспортов                                                                        |
| Форматирование      | стиль кода, стрелочные функции, пустые строки между блоками, prettier                                             |
| Типы и юнит-тесты   | typecheck без ошибок, зелёные тесты                                                                               |
| Миграции            | применяются на чистую БД, сущности не расходятся со схемой                                                        |
| Интеграция          | e2e против настоящего сервера и зависимостей, для каждого драйвера хранилища; вызван каждый эндпоинт спецификации |
| Зависимости и образ | аудит production-зависимостей, сканирование образов на уязвимости                                                 |
| Конфигурация        | схема окружения валидируется при старте                                                                           |

Правило, которое нельзя проверить автоматически (границы между модулями, тонкие
контроллеры, события после транзакции), остаётся предметом code review и описано в
[CONVENTIONS.md](CONVENTIONS.md).

## Проектные исключения

Исключения из общих правил (файлы, которыми владеет генератор маршрутов или ORM;
точки интеграции с фреймворком, где инъекция невозможна; сгенерированные миграции)
фиксируются в конфигурации инструментов и в документации рядом с ними. Исключение
должно быть узким, обоснованным и не распространяться на новый код автоматически.
