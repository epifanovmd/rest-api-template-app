# Данные и миграции

## Схема

- Сущность ORM описывает таблицу: имя таблицы во множественном числе, класс — в
  единственном, колонки — snake_case в БД и camelCase в коде. Nullable-колонка в
  типах — `| null`, а не `undefined`.
- Индексы, уникальные ограничения, каскадные удаления и обнуления объявляются в
  сущности. Целостность данных — обязанность БД, а не кода.
- Схема меняется только миграциями, автосинхронизации нет ни в одном окружении.
  Миграция генерируется из изменений сущностей, проверяется глазами и добавляется в
  явный упорядоченный список миграций. Пока проект не запущен в работу, схема может
  быть собрана в одну начальную миграцию; после запуска каждое изменение — новая
  миграция. CI проверяет, что миграции применяются на чистую БД и что сущности не
  разошлись со схемой.

Оформление сущностей и миграций —
[conventions/entities-migrations](../30-conventions/entities-migrations.md).

## Транзакции и согласованность

- Несколько записей в одной операции изменяются в транзакции (частичный результат
  недопустим). Внутри транзакции используются репозитории менеджера транзакции, а не
  инжектированные.
- Транзакция короткая: без сетевых вызовов и ожидания внешних сервисов внутри.
- Фоновая задача, порождённая изменением данных, ставится в ту же транзакцию
  (outbox): откат отменяет и задачу.
- События публикуются **после** фиксации транзакции. Слушатель никогда не должен
  увидеть незакоммиченное состояние.
- Гонки решаются в БД: атомарный условный `UPDATE` с проверкой числа затронутых
  строк для переходов состояния, идемпотентная вставка для засева, блокировка строки
  для операций, которые не должны идти параллельно. Нарушение уникальности — 409.

## Секреты и чувствительные данные

- Одноразовые секреты (токены сброса, приглашения, ключи) хранятся хешем; сам
  секрет показывается один раз.
- Секреты, которые приложению нужно вернуть в исходном виде (ключи интеграций,
  приватные ключи, пароли для выдачи клиенту), хранятся зашифрованными ключом
  приложения (аутентифицированное шифрование). Ключ — в конфигурации, не в БД;
  в ответы API и логи секрет не попадает без явной необходимости.

## Удаление и бинарные данные

- Данные, у которых важна история (сообщения, аудит), удаляются мягко — флагом и
  очисткой содержимого; справочные данные — жёстко, с каскадами на уровне БД.
- Бинарные данные в БД не хранятся: в таблице — ключ объекта хранилища и метаданные
  ([files](files.md)).
