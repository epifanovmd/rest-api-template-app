# Модульная система и DI

Модуль — класс с декоратором, описывающим его состав:

```ts
@Module({
  imports: [OtherModule], // модули, чьи провайдеры нужны этому
  entities: [Feature], // сущности ORM этого модуля
  providers: [
    Repository,
    Service,
    Controller,
    asSocketListener(Listener),
    asJobHandler(FeatureJob),
  ],
  bootstrappers: [FeatureBootstrap], // опционально: задачи инициализации
})
export class FeatureModule {}
```

## Правила регистрации

- **Модули — единственный источник истины для контейнера.** Декоратор
  `@Injectable()` только помечает класс как пригодный для инъекции; регистрацию
  выполняет исключительно `providers` модуля. `@Injectable()` обязателен на каждом
  инжектируемом классе.
- **Полный список провайдеров** — в `<feature>.module.ts`: репозитории, сервисы,
  контроллеры, обработчики, слушатели, bootstrappers.
- **Контроллеры регистрируются как провайдеры** — генератор маршрутов получает их из
  контейнера.
- **Репозитории** помечаются `@InjectableRepository(Entity)`: загрузчик модулей сам
  создаёт их поверх подключения к БД для указанной сущности.
- **Сущности** перечисляются в `entities` модуля-владельца. Подключение к БД
  собирает их из дерева модулей, без поиска файлов по маске; тест реестра падает,
  если сущность объявлена, но не зарегистрирована.
- **Провайдер по токену** (`{ provide: TOKEN, useClass }`, обычно через хелпер
  `asXxx(Cls)`) используется для multi-inject: несколько реализаций одного контракта
  собираются по символу. Это основной механизм расширения —
  [extension-points](extension-points.md).
- **Абстрактный класс как токен** — для контракта с одной реализацией, выбираемой
  конфигурацией (очередь задач, хранилище файлов): потребитель инжектит абстракцию,
  инфраструктурный модуль привязывает реализацию.
- Все провайдеры — singleton. Повторная регистрация одного класса игнорируется.
- Корневой модуль перечисляет все модули приложения; каждый модуль регистрируется в
  нём один раз. Порядок важен только там, где один модуль собирает реализации из
  других по токену: такой модуль идёт последним.
- Зависимости приходят через конструктор. Прямое обращение к контейнеру допустимо
  только в composition root и в точках интеграции с фреймворком (аутентификация
  маршрутов, middleware генератора маршрутов), где инъекция невозможна.

## Контракты и инверсия зависимостей

Контракт принадлежит потребителю. Интерфейс для каждого сервиса с единственной
реализацией не создаётся: DI-контейнер и так позволяет подменить класс в тестах.
Инверсия зависимостей применяется на границах:

- транспорт реального времени (эмиттер, а не сервер);
- почта, push, внешние API;
- хранилище файлов;
- часы и генераторы случайных значений — для тестов;
- инфраструктурный модуль, который собирает реализации из доменных модулей:
  контракт и токен внизу, реализации — в доменных модулях.

Композиция предпочтительнее наследования: инъекция через конструктор для сервисов,
декораторы для сквозного поведения маршрута (валидация, guards, security), события
для реакции между модулями. Наследование — при стабильном базовом контракте:
базовый репозиторий, базовый DTO.
