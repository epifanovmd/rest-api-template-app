# События и реальное время

Событийная модель — единственный способ, которым модули реагируют друг на друга:

```
Service ──emit──▶ EventBus ──▶ Listener ──▶ эмиттер реального времени ──▶ клиент
                        └────▶ Listener другого модуля (побочный эффект: задача, аудит)
```

## EventBus

- Событие — класс с неизменяемыми полями (readonly). Ключ подписки — сам класс, а не
  строковое имя: это безопасно при сборке и даёт типизацию.
- Синхронная публикация — fire-and-forget с изоляцией ошибок обработчиков.
  Асинхронная — параллельное ожидание всех обработчиков без прерывания на первой
  ошибке. Выбор определяется тем, нужно ли сервису дождаться побочных эффектов.
- EventBus — внутрипроцессный. Надёжный побочный эффект, который должен пережить
  сбой (письмо, push, вебхук, обработка файла), слушатель не выполняет сам, а ставит
  задачей в очередь ([jobs](jobs.md)).
- Событие публикуется после фиксации транзакции ([data](data.md)). Долгая операция
  не блокирует ответ: результат доставляется событием.

## Реальное время

- **Обработчик соединения** (клиент → сервер) регистрируется по токену и подписывает
  входящие события только через валидирующую обёртку: схема входа, лимит частоты на
  соединение и событие, ответ-подтверждение с машинным кодом ошибки.
- **Слушатель событий** (EventBus → клиент) отправляет данные только через
  сервис-эмиттер: адресно пользователю (все его устройства), в комнату или всем.
  Эмиттер работает через общий адаптер — событие доходит до соединений на любом
  процессе.
- События не буферизуются: пропущенное за время обрыва клиент восстанавливает,
  перечитав состояние после переподключения.
- Карты событий клиент → сервер и сервер → клиент типизированы. Модуль транспорта
  объявляет только события соединения; каждый модуль дополняет карты своими
  событиями в своём файле. Новое событие сначала добавляется в карту, затем
  используется.
- Инфраструктура реального времени запускается bootstrapper-ом после всех модулей и
  при остановке снимает свои записи присутствия.

## Комнаты

- Личная комната пользователя — при подключении; комнаты доменных сущностей — через
  провайдеров комнат (восстанавливаются при переподключении) или по запросу клиента
  с проверкой политикой комнаты.
- Запрос на вход в комнату принимается сразу после установки соединения, до
  регистрации присутствия: клиент подписывается в момент подключения и
  переподключения.
- **Сущности с владельцем:** в комнату списка входит только держатель права
  просмотра на все; пользователь с областью «свои» получает изменения лично, если он
  владелец или создатель сущности. Когда сущность перестаёт быть своей (сменился
  владелец), бывшему владельцу отправляется её снятие, а его комнаты пересматриваются.

## Устройство подсистемы

```text
Server service     — обёртка над библиотекой, жизненный цикл
Auth middleware    — проверка токена при подключении
Client registry    — кто подключён, на скольких устройствах
Emitter service    — единственный способ отправить клиенту: адресно, в комнату, всем
Bootstrapper       — запуск, сбор handlers/listeners по токенам, остановка
Domain listener    — подписка на события своего модуля → вызов эмиттера
Domain handler     — входящие события своего модуля → проверка прав → действие
```

Детали библиотеки скрыты в сервисе сервера; обработчик и слушатель — разные
контракты с разными потребителями; доменные модули зависят от контрактов и
эмиттера, а не от сервера; сервисы о транспорте не знают.
