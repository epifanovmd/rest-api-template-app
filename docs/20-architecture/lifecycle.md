# Жизненный цикл, роли процесса и запуск

## Запуск

Порядок фиксирован и ориентирован на работу под оркестратором:

0. **Инструментирование** — отправка ошибок подключается первым импортом точки
   входа, до загрузки остальных модулей.
1. **HTTP-сервер и системные маршруты** поднимаются первыми — liveness-проба отвечает
   сразу, даже если остальное ещё не готово.
2. **База данных** — подключение с бесконечным retry и экспоненциальной задержкой.
   Сервер не падает без БД: он ждёт и отдаёт readiness = 503.
3. **Миграции** — применяются при старте под блокировкой БД либо отдельным шагом
   развёртывания. В режиме «миграции отдельным шагом» отставшая схема — ошибка запуска.
4. **Модули и DI** — загрузчик обходит дерево модулей и регистрирует провайдеры.
5. **Маршруты приложения** — после модулей, потому что маршруты резолвят
   контроллеры и провайдеры маршрутов из контейнера. В роли воркера не регистрируются.
6. **Bootstrappers** — инициализация модулей (seed, запуск очереди задач, сокетов).
   Bootstrapper сам объявляет, критичен ли он: некритичный при ошибке пропускается с
   предупреждением, критичный — прерывает запуск.
7. **Готовность** — readiness-проба возвращает 200, пока бутстраперы завершены и БД
   доступна (фоновая проверка); потеря БД снимает реплику с трафика.

## Остановка

По сигналу: readiness = 503 → пауза, чтобы балансировщик снял реплику → HTTP-сервер
перестаёт принимать соединения и ждёт in-flight запросы (по таймауту рвёт
оставшиеся) → bootstrappers уничтожаются в обратном порядке с изоляцией ошибок
(активные задачи дорабатывают до своего таймаута, затем возвращаются в очередь) →
подписки EventBus снимаются → закрывается БД → накопленные ошибки отправляются.

Сигналы обрабатываются один раз; при превышении общего таймаута процесс завершается
принудительно. Необработанное исключение переводит процесс в останов, необработанный
reject промиса — логируется и отправляется в трекер ошибок.

Системные маршруты (liveness, readiness, health, метрики) не принадлежат ни одному
модулю, не проходят через аутентификацию, CORS и лимит запросов.

## Роли процесса

Один образ и один код запускаются в одной из ролей (переменная окружения `APP_ROLE`):

| Роль     | HTTP                   | Клиентские сокеты | Очередь задач                        |
| -------- | ---------------------- | ----------------- | ------------------------------------ |
| `api`    | API и системные пробы  | да                | только постановка                    |
| `worker` | только системные пробы | нет               | выполнение задач и расписаний        |
| `all`    | API и системные пробы  | да                | постановка и выполнение (разработка) |

Воркер не принимает клиентов реального времени, но его слушатели событий отправляют
клиентам через общий адаптер реального времени, поэтому событие, возникшее в задаче,
доходит до клиента, подключённого к любому API-процессу. Тяжёлые зависимости
(обработка медиа) нужны только образу воркера.

## Несколько реплик

Приложение рассчитано на горизонтальное масштабирование API за балансировщиком и
отдельные процессы-воркеры. Всё, что должно быть согласовано между процессами,
хранится вне процесса: лимиты запросов, присутствие пользователей, комнаты
real-time транспорта, отзыв токенов, кэши прав — в Redis; одноразовые секреты,
сессии и задачи — в БД. Периодическую задачу выполняет ровно один процесс кластера —
это гарантирует очередь задач, а не таймеры в процессе. Клиентский IP и протокол
берутся из заголовков прокси только при явно доверенном прокси.

Два общих механизма ядра для согласования процессов:

- **Сигналы между процессами** — LISTEN/NOTIFY основной БД: одно соединение на
  набор каналов модуля, переподключение после обрыва. Сигнал, отправленный в
  транзакции, доходит только после её фиксации. Без LISTEN (пулер в режиме
  транзакций, обрыв) подписчики переходят на опрос — механизм сообщает о своём
  состоянии. Модуль объявляет свои каналы, а не открывает своё соединение.
- **Живое состояние с TTL** (последние снимки, счётчики, отметки) — общее
  хранилище ядра поверх Redis с атомарными операциями; без Redis — память
  процесса, только для однопроцессного режима. Модуль работает в своём
  пространстве ключей.

## Сборка и запуск

- Сборка — компилятор TypeScript, без шагов копирования. Всё, что код читает в
  рантайме, либо импортируется (JSON-спецификация), либо лежит в каталоге ассетов
  вне исходников (шаблоны писем по локалям) и находится по пути от корня проекта —
  одинаково в разработке, сборке и контейнере.
- Сборка сохраняет имена классов: ORM, DI и EventBus используют классы как ключи.
  Минификация с искажением имён запрещена.
- Тесты исключаются из production-сборки.
- Запуск без явного окружения — production с безопасными умолчаниями.
- **Образ** один, с двумя целями сборки: API — без тяжёлых системных зависимостей,
  воркер — с ними. Многостадийная сборка, непривилегированный пользователь,
  init-процесс как PID 1, файловая система только для чтения.
- **Развёртывание:** образ собирается и публикуется в registry по тегу релиза; на
  сервере образ только скачивается. Порядок: одноразовый шаг миграций → API
  (масштабируемый) и воркер. Приложение само схему не меняет (миграции при старте
  выключены). Инфраструктура (БД, Redis, S3-совместимое хранилище с созданием bucket)
  — в том же описании развёртывания и заменяется внешними сервисами конфигурацией.
- Для разработки — отдельное описание инфраструктуры: БД, Redis, тестовый SMTP и
  S3-совместимое хранилище.
