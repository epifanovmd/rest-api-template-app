# Модульный монолит и топология

Технологические решения (HTTP-фреймворк, генератор маршрутов, DI-контейнер, ORM,
транспорт реального времени, валидатор, очередь задач, хранилище) описываются в
`docs/20-architecture` категориями, а не брендами: архитектура не зависит от
конкретной библиотеки. Актуальный выбор фиксируется в README проекта.

## Модульный монолит

Сервер — модульный монолит: одна кодовая база, одна база данных, один образ, но код
разбит на изолированные модули с явными границами. Модуль — единица владения: он
владеет своими таблицами, бизнес-правилами, HTTP-контрактом, событиями, ошибками,
правами и фоновыми задачами. Один и тот же код запускается в разных ролях процесса
([lifecycle](lifecycle.md#роли-процесса)).

```
src/
  main.ts            ← точка входа: инструментирование, запуск, graceful shutdown, фатальные ошибки
  app.ts             ← жизненный цикл приложения (composition root)
  app.module.ts      ← корневой модуль: список всех модулей приложения
  app.container.ts   ← единственный экземпляр IoC-контейнера
  config.ts          ← валидированная конфигурация окружения
  core/              ← ядро: DI, модули, auth, ошибки, события, контракты задач и хранилища, наблюдаемость
  common/            ← универсальные хелперы без знания о домене и инфраструктуре
  middleware/        ← сквозные HTTP-middleware и порядок их регистрации
  routing/           ← сгенерированные маршруты, спецификация, системные маршруты
  migrations/        ← миграции схемы БД
  types/             ← глобальные типы и declaration augmentation
  test/              ← общая тестовая инфраструктура (фабрики моков)
  modules/           ← доменные и инфраструктурные модули
    <feature>/       ← один модуль = одна предметная область или одна инфраструктурная подсистема
test/e2e/            ← интеграционный набор против настоящего сервера
```

```text
core → common          ← фундамент: контракты и реестры, ничего не знает о модулях
middleware / routing   ← сквозной HTTP-слой, ничего не знает о конкретных модулях
modules/<feature>      ← один модуль = одна предметная область или одна инфраструктурная подсистема
app.*                  ← composition root: собирает модули, запускает приложение
```

## Области

| Область      | Что здесь находится                                                                                                                    | Контрольный вопрос                                         |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `core`       | декораторы, загрузчик модулей, DI-токены и реестры, базовые классы, auth, ошибки, EventBus, контракты задач и хранилища, наблюдаемость | Без этого не заработает ни один модуль?                    |
| `common`     | чистые функции-хелперы, пригодные в любом проекте                                                                                      | Это пригодилось бы в любом другом проекте?                 |
| `middleware` | обработка каждого HTTP-запроса до маршрутизации                                                                                        | Это должно происходить для всех маршрутов без исключения?  |
| `routing`    | связывание контроллеров с HTTP-сервером: генерируемые маршруты, спецификация, системные пробы и метрики                                | Это связывает контроллеры с сервером, а не бизнес-логика?  |
| `modules`    | бизнес-логика и инфраструктурные подсистемы (очередь, хранилище, сокеты — тоже модули), каждая — в своём модуле                        | У этого есть владелец — предметная область или подсистема? |
| `app.*`      | список модулей, жизненный цикл                                                                                                         | Это про сборку приложения, а не про его поведение?         |

Направление знаний между областями — [dependencies](dependencies.md). Устройство
модуля изнутри — [module-layers](module-layers.md).
