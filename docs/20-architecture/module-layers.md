# Слои и анатомия модуля

## Слои

```
HTTP-запрос / задача / событие клиента
   │
   ▼
Controller · JobHandler · SocketHandler  ← вход: контракт, security, валидация, контекст
   │
   ▼
Service      ← бизнес-правила, транзакции, доменные события, постановка задач, возвращает DTO
   │
   ▼
Repository   ← доступ к данным: запросы, выборки, без бизнес-правил
   │
   ▼
Entity       ← схема таблицы и связи
```

| Слой       | Знает о                                    | Не знает о                                      |
| ---------- | ------------------------------------------ | ----------------------------------------------- |
| Controller | Service, DTO, схемы валидации              | Repository, Entity, транспорт реального времени |
| JobHandler | Service, контекст задачи                   | HTTP, транспорт реального времени               |
| Service    | Repository, Entity, DTO, EventBus, очередь | HTTP-контекст, транспорт реального времени      |
| Repository | Entity, ORM                                | DTO, бизнес-правила, события                    |
| Listener   | EventBus, эмиттер реального времени, DTO   | HTTP, Repository (кроме чтения для адресации)   |

## Ключевые границы

- **Контроллер и обработчик задачи тонкие.** Они объявляют контракт и делегируют.
  Бизнес-условия, запросы к БД и формирование ответа в них запрещены.
- **Наружу уходит только DTO.** Сущность ORM никогда не возвращается из контроллера
  и не отдаётся в события: DTO — единственная форма данных на границе модуля, даже
  если поля совпадают.
- **Сервис не знает о транспорте.** Он публикует доменное событие; кто и куда его
  доставит — ответственность слушателей.
- **Репозиторий не принимает решений.** Он умеет искать и сохранять; проверка прав,
  статусов и инвариантов — в сервисе.
- **Валидация входа — на границе.** Схема валидации применяется декоратором на
  методе контроллера или обёрткой входящего события реального времени; сервис
  получает уже проверенные данные и проверяет только бизнес-инварианты.

Сигналы нарушения: контроллер строит запрос к БД; репозиторий бросает «нет доступа»;
сервис читает заголовки; слушатель принимает бизнес-решения. Сервис, который
одновременно проверяет права, строит запрос к ORM, отправляет письмо и формирует
ответ для транспорта, делится: права и инварианты — в сервисе, запрос — в
репозитории, письмо и доставка — в слушателях событий. Линейная операция при этом не
дробится на одноразовые приватные методы.

## Владелец побочного эффекта

У побочного эффекта явный владелец жизненного цикла:

- запись в БД — в транзакции сервиса;
- доставка клиенту — в слушателе, после фиксации;
- подписка на события — в `register()`, снятие — при остановке;
- таймер — запуск в bootstrapper-е, остановка в `destroy`; периодическая работа —
  задачей очереди с расписанием ([jobs](jobs.md));
- повторная инициализация безопасна либо запрещена контрактом.

## Сервис или репозиторий

`repository` — как достать и сохранить: условия выборки, связи, сортировка, пагинация.
Не бросает бизнес-исключений и не знает о правах.

`service` — что можно и что должно произойти: проверка прав и статусов, инварианты,
транзакции, публикация событий, постановка задач, сборка DTO.

Если метод репозитория начинает проверять «можно ли» — он должен быть в сервисе.
Если сервис пишет условия запроса к ORM — они должны быть в репозитории.

## Анатомия модуля

```text
modules/<feature>/
  index.ts                     ← public API модуля
  README.md                    ← сущности, эндпоинты, события, задачи, ошибки модуля
  <feature>.module.ts          ← декларация @Module: imports, entities, providers, bootstrappers
  <feature>.entity.ts          ← сущность ORM (одна на файл; вспомогательные — свои файлы)
  <feature>.repository.ts      ← доступ к данным
  <feature>.service.ts         ← бизнес-логика
  <feature>.controller.ts      ← HTTP-контракт
  <feature>.types.ts           ← enum-ы, const-объекты, лимиты домена
  <feature>.errors.ts          ← доменные ошибки с кодами <PREFIX>_<KEY>
  <feature>.permissions.ts     ← права модуля в реестре прав (если есть)
  <feature>.access.ts          ← доступ «все / свои» к сущности с владельцем (если есть)
  <feature>.config.ts          ← настройки модуля из окружения (если есть)
  <feature>.socket-events.ts   ← события реального времени модуля (если есть)
  <aspect>.job.ts              ← обработчик очереди задач (если есть)
  <feature>.handler.ts         ← обработчик входящих событий реального времени (если есть)
  <feature>.listener.ts        ← слушатель EventBus → реальное время / задачи (если есть)
  <feature>.bootstrap.ts       ← задача инициализации (если есть)
  dto/                         ← DTO ответов и интерфейсы тел запросов
  validation/                  ← схемы валидации входа
  events/                      ← классы доменных событий
  <feature>.service.test.ts    ← тесты рядом с кодом
```

- Маленький модуль может не иметь части файлов; пустые директории не создаются.
- Модуль без HTTP (только сервис для других модулей) — нормальная ситуация.
- Модуль с несколькими контроллерами или сервисами именует их по ответственности
  (`<feature>-<aspect>.controller.ts`).
- Реализации чужих контрактов (политика, провайдер комнат, проба) — отдельные файлы
  с суффиксом роли.

Именование файлов и классов — [conventions/naming](../30-conventions/naming.md).
