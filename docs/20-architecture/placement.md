# Куда положить новый код

Код кладётся в модуль-владелец, а не «где удобно». Если место не определяется этим
документом однозначно — вопрос пользователю, а не новое решение.

## Дерево решений

**HTTP-эндпоинт.** Метод в контроллере модуля-владельца; отдельная группа маршрутов
той же области — второй контроллер модуля; новая предметная область — новый модуль.
Маршрут, который нельзя описать контроллером (поток, подписанная загрузка), —
провайдер маршрутов модуля, описанный в README модуля. Правила контроллера —
[conventions/controllers](../30-conventions/controllers.md).

**Бизнес-правило.** Правило сущности или сценария — сервис модуля-владельца. Правило
затрагивает несколько модулей — сервис модуля, который инициирует операцию;
остальные реагируют на событие. Проверка формы входа (длина, формат,
обязательность) — схема в `validation/`, а не сервис. Нарушение правила — доменная
ошибка из `<feature>.errors.ts`, а не новое исключение по месту.

**Запрос к БД.** Выборка или сохранение — метод репозитория модуля-владельца
сущности. Чтение чужой сущности — через репозиторий модуля-владельца из его public
API; свой репозиторий на чужую сущность не создаётся. Несколько записей за
операцию — транзакция в сервисе; конкурентный переход состояния — условный `UPDATE`
в репозитории ([data](data.md)).

**Поле или таблица.** Поле — сущность + новая миграция + отражение в DTO и схеме
валидации (длины совпадают). Новая сущность области — отдельный файл в том же
модуле. Enum или набор констант — `<feature>.types.ts`, не файл сущности.

**Ответ API.** Форма ответа — DTO в `dto/`; тело запроса — интерфейс
`I<Action>Body` в `dto/`, схема — в `validation/`; список и лента — единые страницы
из `core` ([http](http.md#пагинация)); DTO со ссылками на файлы принимает заранее
подписанную карту файлов.

**Реакция на изменение в другом модуле.** Всегда событие: источник публикует класс
события из своего `events/`, потребитель подписывается в своём слушателе. Побочный
эффект, который должен пережить сбой (письмо, push, вебхук), — слушатель ставит
задачу ([events-realtime](events-realtime.md)).

**Фоновая или периодическая работа.** Долгая или ненадёжная работа — обработчик
очереди `<aspect>.job.ts`; порождённая изменением данных — постановка в той же
транзакции; отложенное действие (таймаут) — задача с отложенным запуском, при
необходимости с периодической «страховкой»; периодическая работа — обработчик с
расписанием, не таймер в bootstrapper-е ([jobs](jobs.md)).

**Файл.** Хранение по ключу с раскладкой в модуле-владельце, выдача подписанной
ссылкой, крупная загрузка — ссылка на запись + подтверждение, обработка — задачей,
ссылка домена на файл — проба использования ([files](files.md)).

**Схема аутентификации.** Новый вид вызывающего — класс схемы в модуле-владельце,
регистрация `asSecurityScheme`, описание схемы в конфигурации генератора маршрутов;
ядро и другие схемы не меняются ([access](access.md)).

**Комната реального времени.** Автоматический вход — провайдер комнат модуля
(`asSocketRoomProvider`); вход по запросу — политика комнаты (`asSocketRoomPolicy`)
с типом комнаты и проверкой права; изменение членства — слушатель вводит и выводит
соединения через эмиттер; новое событие — дополнение карт в
`<feature>.socket-events.ts` ([events-realtime](events-realtime.md)).

**Право.** Объявить в `<feature>.permissions.ts` через реестр прав и использовать в
security-scope; общий список прав не правится. Сущность с владельцем — право с
областью, `<feature>.access.ts`, маршрут с `:own`, список с `mine` ([access](access.md)).

**Задача при старте.** Seed, прогрев, запуск подсистемы — bootstrapper модуля в
`bootstrappers` его `@Module`; некритичный объявляет `critical = false`.
Периодическая работа — не сюда, а в очередь задач с расписанием.

**Параметр окружения.** Настройка платформы — схема в `config.ts`; настройка модуля —
`<feature>.config.ts` через `defineModuleConfig` ([config](config.md)).

**Письмо.** Файлы шаблона во всех локалях каталога шаблонов писем + дополнение
`IMailTemplateData` в файле письма модуля (`declare module`); тест полноты проверит
наборы по локалям.

**Вспомогательная функция.** Не знает о домене и инфраструктуре — `common/`; часть
механики ядра (DI, auth, ошибки, события, контракты) — `core/`; нужна одному модулю —
внутри модуля рядом с потребителем.

## Middleware или guard

`middleware` — сквозное поведение для каждого запроса (идентификатор, логирование,
CORS, лимиты, разбор тела), без знания о маршруте; живёт в `middleware/` вместе с
порядком регистрации.

`guard` — защита конкретного маршрута (лимит на эндпоинт, HTTPS, whitelist),
объявляемая декоратором на методе контроллера; лежит в `core/guards`. Guard может
иметь параметры (лимит, заголовок, список адресов) и собственное изолированное
состояние.

Аутентификация и проверка прав — ни то, ни другое: это схема безопасности генератора
маршрутов, объявляемая декоратором на методе.

## Событие, задача или прямой вызов

Прямой вызов сервиса другого модуля допустим, когда результат нужен в этом же
запросе для продолжения операции и зависимость идёт в одну сторону без цикла.

Событие обязательно, когда это реакция на факт («создано», «изменено», «удалено»), а
не запрос данных; потребителей может быть несколько или они появятся позже;
потребитель — инфраструктура (реальное время, push, почта, аудит); прямой вызов
создал бы обратную или циклическую зависимость.

Задача обязательна, когда работа долгая, тяжёлая или зависит от внешней системы;
эффект должен пережить сбой процесса и повториться; работа периодическая или
отложенная.

Событие публикуется после фиксации транзакции и несёт DTO или идентификаторы, а не
сущности ORM. Задача ставится в той же транзакции, что и данные.

## Новый модуль: порядок действий

1. Каркас по конвенциям — генератором модуля (команда —
   [ops/commands](../70-ops/commands.md)): сущность, репозиторий, сервис, контроллер,
   DTO, схемы, ошибки, события, модуль, README и тесты.
2. Доработать сущность → сгенерировать миграцию → добавить её в список миграций.
3. Сервис с бизнес-логикой, событиями, задачами; DTO; схемы валидации; ошибки.
4. Контроллер: маршруты под версией, security-scopes с правами, валидация тел,
   статусы 201/204.
5. При необходимости — права, обработчики задач, слушатель и обработчик реального
   времени, провайдеры и политики комнат, bootstrapper. У сущности с владельцем —
   права с областью, `<feature>.access.ts`, рассылка изменений своим.
6. `index.ts` — только то, что нужно другим модулям.
7. Зарегистрировать модуль в корневом модуле (до модуля, собирающего реализации по
   токену).
8. Юнит-тесты сервиса и схем; e2e-сценарии для каждого нового эндпоинта.
9. Перегенерировать маршруты и спецификацию; описать модуль в его `README.md`.
