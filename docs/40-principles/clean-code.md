# Чистый код

Принципы — инструменты, а не цель. Сначала простое корректное решение, затем
оправданная абстракция. SOLID и паттерны проектирования —
[solid-patterns](solid-patterns.md).

## Приоритеты

Хороший код: 1) корректно решает текущую задачу; 2) читается без устного
объяснения; 3) безопасно изменяется; 4) не содержит сложности без причины.

## Порядок работы

1. Сформулировать требуемое поведение и его владельца (модуль).
2. Определить владельца данных и побочных эффектов.
3. Написать простейшее решение в нужном месте.
4. Дать предметные имена.
5. Отделить вычисления и бизнес-правила от I/O (данные, транспорт).
6. Убрать подтверждённое дублирование.
7. Проверить тестами, typecheck и lint.

## KISS

Решение с минимальной когнитивной нагрузкой: ранний `return` вместо вложенности,
функция вместо класса без состояния, явная последовательность вместо магии,
несколько понятных условий вместо универсального движка, локальное решение вместо
преждевременного фреймворка. Простота — не минимум строк: две именованные переменные
бывают понятнее одного выражения.

## YAGNI

Без текущего требования или существующей точки расширения не создаются: generic API
для одного сценария, base class без наследников, plugin system без плагинов,
неиспользуемые options, repository поверх одного вызова, флаги для несуществующих
вариантов. Новый код «на будущее» не пишется. Существующий неиспользуемый код
(сервисы, экспорты, методы) может быть заготовкой: он не удаляется в рамках
рефакторинга или задачи без явной команды пользователя — находка сообщается в отчёте.

## DRY

DRY — о знании, а не о форме кода.

- Выносить общее, когда повторяется одно бизнес-правило, исправление требует
  синхронно менять несколько мест, копии обязаны вести себя одинаково.
- Не объединять, когда сходство случайно, сценарии развиваются независимо, общая
  функция обрастает флагами, абстракции нельзя дать предметное имя.

Небольшое повторение безопаснее неправильной абстракции.

## Когда рефакторить

Сигналы: одно изменение требует правок в несвязанных местах; функции нельзя дать
короткое имя; модуль меняется по разным причинам; растут флаги и ветвления; тест
требует много инфраструктуры; наружу импортируют внутренние детали; поведение опасно
менять из-за скрытых side effects.

Сначала зафиксировать поведение тестом. Менять структуру небольшими шагами, не
смешивая рефакторинг с новым поведением.
