# SOLID и паттерны

## Правило выбора

Паттерн применяется только к сформулированной проблеме. Перед внедрением:

1. Какая проблема уже существует?
2. Почему функция или простой объект её не решает?
3. Станет ли основной сценарий понятнее?
4. Есть ли реальные варианты или внешняя граница?
5. Можно ли удалить паттерн без потери поведения?

Проблема не формулируется — паттерн не нужен.

## SOLID

- **S** — одна ответственность и одна причина измениться. Модуль, который сразу
  получает данные, проверяет вход, применяет бизнес-правило и формирует представление
  (UI или ответ), делится на сценарий, инфраструктуру и представление. Линейную операцию не дробить на одноразовые функции.
- **O** — стабильный код расширяется добавлением варианта. Strategy/registry — когда
  варианты уже есть и меняются независимо; пока их мало — `if`/`switch`.
- **L** — реализация честно соблюдает контракт: те же входы, совместимый результат,
  обещанные side effects, без скрытых условий и неожиданных ошибок. Часть реализаций
  не поддерживает метод — интерфейс выбран неверно.
- **I** — потребитель зависит только от нужной части API. Делить интерфейс при разных
  потребителях, а не ради количества файлов.
- **D** — высокоуровневая логика зависит от контракта, инфраструктура реализует. На
  границах: storage, HTTP/socket, notifications, analytics, platform API,
  clock/randomness для тестов. Контракт принадлежит потребителю; интерфейс для
  каждого класса с одной реализацией не создаётся.

## Композиция вместо наследования

Функции и небольшие объекты для поведения, constructor injection для сервисов,
Strategy callback для алгоритма, сборка из заменяемых частей для представления. Наследование — при настоящем отношении
«является» и стабильном базовом контракте.

## Паттерны

| Проблема                       | Паттерн              | Когда                                        |
| ------------------------------ | -------------------- | -------------------------------------------- |
| скрыть API библиотеки          | Adapter              | внешний API не должен протекать в приложение |
| простой вход в подсистему      | Facade               | несколько шагов всегда выполняются вместе    |
| взаимозаменяемые алгоритмы     | Strategy             | варианты меняются независимо                 |
| создание зависит от окружения  | Factory              | выбор реализации не принадлежит потребителю  |
| код не должен знать реализацию | Dependency Injection | есть важная внешняя граница                  |
| реакция на изменение состояния | Observer             | подписка один-ко-многим                      |
| успех и ошибка ожидаемы        | Result               | оба исхода — нормальный поток                |
| целое из заменяемых частей     | Composition          | части заменяются независимо                  |

Пример инфраструктурного модуля: сервис (публичные операции) за контрактом,
adapter библиотеки, регистрация в composition root; потребитель вызывает контракт и
не знает библиотеку. Factory и Strategy не добавляются, пока нет
нескольких способов создания или алгоритмов.

## Частые ошибки

Паттерн ради названия; интерфейс для каждого класса; любое повторение как нарушение
DRY; абстракция «на будущее»; простой сценарий за generic framework; наследование
ради пары строк; Strategy для одного алгоритма; деление API без разных потребителей.
