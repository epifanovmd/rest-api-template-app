# ALP v1 — Agent Link Protocol

Протокол связи **агента** (долгоживущий процесс на узле: сервер, VM, контейнер) с
бэкендом. Нормативный документ: реализации (бэкенд — модуль `agent`, Go — `agent/kit/alp`,
Python — `python/worker_sdk`) обязаны ему следовать и проходят тесты на эталонных
сообщениях из [`fixtures/`](fixtures).

Протокол задаёт агент: бэкенд — одна из сторон, реализующих контракт, а не его владелец.
Изменение протокола начинается с этого документа и fixtures.

## 1. Принципы

1. **Соединение открывает только агент.** Агенту не нужны входящие порты; он работает
   за NAT и прокси.
2. **Автономность.** Потеря связи — штатный режим. Агент продолжает работу, копит
   результаты в журнале на диске (outbox) и досылает их после переподключения.
3. **Сервер → агент — по состоянию, агент → сервер — по сообщениям.** Всё, что сервер
   поручает агенту (задача, команда, желаемое состояние), выводится из состояния в БД
   и доставляется заново после переподключения. Агент обрабатывает повторную доставку
   идемпотентно (по id). Всё, что агент сообщает серверу, проходит один из трёх классов
   доставки (§4).
4. **Транспорт взаимозаменяем.** WebSocket — основной, HTTP sync — запасной; сообщения
   одинаковы, логика сессии на сервере от транспорта не зависит.
5. **Версия и возможности согласуются явно** в рукопожатии (§3).

## 2. Транспорт

### 2.1 WebSocket (основной)

```
GET /api/v1/agent-link
Upgrade: websocket
Sec-WebSocket-Protocol: alp.v1
Authorization: Agent <agentId>.<secret>
```

- Один текстовый кадр — одно сообщение (JSON, UTF-8).
- Живость — WS ping/pong: каждая сторона пингует раз в 20 с; без pong за 10 с соединение
  закрывается и агент переподключается.
- Ошибка авторизации отдаётся **до** upgrade кодом HTTP: `401` — учётные данные неверны или
  отозваны, `403` — агент заблокирован, `426` — нет подходящего подпротокола.

**Коды закрытия:**

| Код  | Кто    | Смысл                                                          | Реакция агента                                  |
| ---- | ------ | -------------------------------------------------------------- | ----------------------------------------------- |
| 1000 | любой  | штатное закрытие                                               | переподключиться (если не останавливается)      |
| 1001 | агент  | агент останавливается                                          | —                                               |
| 1012 | сервер | сервер перезапускается                                         | переподключиться сразу, с джиттером ≤ 1 с       |
| 4400 | сервер | нарушение протокола: нет `hello` за 10 с, невалидное сообщение | переподключиться с backoff, сообщить в лог      |
| 4401 | сервер | учётные данные отозваны                                        | повторная регистрация (§5), иначе backoff       |
| 4409 | сервер | нет общей версии протокола                                     | backoff, ждать обновления (`hello` повторяется) |
| 4410 | сервер | подключилась другая сессия того же агента                      | не переподключаться 30 с, затем backoff         |
| 4429 | сервер | перегрузка; `reason` — секунды до повтора                      | переподключиться не раньше указанного           |

### 2.2 HTTP sync (запасной)

Когда WebSocket недоступен (прокси режет upgrade, `404/400/426` на upgrade), агент
переходит на обмен пачками тех же сообщений:

```
POST /api/v1/agent-link/sync
Authorization: Agent <agentId>.<secret>
{ "sessionId": "…" | null, "messages": [ …конверты… ], "waitSeconds": 0..25 }
→ 200 { "sessionId": "…", "messages": [ …конверты… ] }
```

- Первый запрос сессии несёт `hello` первым сообщением и `sessionId: null`; ответ содержит
  `welcome`.
- Сервер обрабатывает входящие по порядку, затем отвечает доставками. Если доставлять
  нечего, ждёт до `waitSeconds`: новую задачу, команду или изменение состояния.
- Сессия, которую сервер уже забыл, — ответ `409` с кодом `AGENT_SESSION_EXPIRED`: агент
  начинает новую сессию с `hello`.
- Агент в режиме HTTP раз в 10 минут пробует вернуться на WebSocket.

## 3. Рукопожатие

```
агент                                сервер
  │── hello ─────────────────────────▶│  проверка версии и возможностей
  │◀──────────────────────── welcome ─│  или закрытие 4409
  │◀─ доставки (job.assign, cmd.run, state.put, job.cancel …)
  │── status / metrics / … ──────────▶│
```

- `hello` — первое сообщение сессии; другие сообщения до `welcome` запрещены. Без `hello`
  за 10 с — закрытие 4400. Без `welcome` за 15 с агент рвёт соединение сам.
- `hello.protocols` — версии, которые знает агент; сервер выбирает наибольшую общую и
  возвращает в `welcome.protocol`. Общей нет — закрытие 4409.
- В `hello` агент перечисляет **возможности** (`capabilities`) и задачи, которые он
  держит (`jobs`): выполняющиеся **и завершённые без связи, чей итог ещё в outbox**.
  Сервер сверяет их с БД (§6.3) до досылки outbox, поэтому задача с недоставленным
  итогом обязана быть в списке — иначе сервер сочтёт её потерянной.
- `welcome.config` — серверные настройки сессии (интервалы, лимиты). Позже их меняет
  сообщение `config`.

## 4. Конверт и классы доставки

```json
{ "type": "job.complete", "id": "0f8c…", "re": "…", "seq": 42, "ts": 1791380000000, "data": { … } }
```

| Поле   | Тип             | Обязательно             | Смысл                                             |
| ------ | --------------- | ----------------------- | ------------------------------------------------- |
| `type` | string          | да                      | тип сообщения, `<область>.<действие>`             |
| `id`   | string (≤ 64)   | для надёжных и запросов | уникальный id сообщения (UUID/ULID)               |
| `re`   | string          | для ответов             | `id` сообщения, на которое это ответ              |
| `seq`  | integer ≥ 1     | для потоковых           | номер в потоке агента; растёт в пределах `bootId` |
| `ts`   | integer, мс UTC | нет                     | время создания на стороне отправителя             |
| `data` | object          | по типу                 | полезная нагрузка                                 |

Неизвестные поля игнорируются (forward compatibility). Неизвестный `type` от агента —
`error` с кодом `UNKNOWN_TYPE` (сессия не рвётся). Неизвестный `type` от сервера агент
логирует и пропускает.

**Классы доставки агент → сервер:**

| Класс        | Гарантия                                   | Механизм                                                                                                                                                                                                | Сообщения                                                                          |
| ------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **поток**    | по порядку, без повторов, может потеряться | `seq` в пределах `bootId`; сервер подтверждает `ack{seq}`; агент держит неподтверждённое в ограниченном буфере памяти и досылает после переподключения; сервер отбрасывает `seq ≤ последнего принятого` | `status`, `metrics`, `job.accept`, `job.progress`, `cmd.accept`, `cmd.output`      |
| **надёжный** | как минимум один раз, переживает рестарт   | `id`; журнал на диске (outbox) до `ack{ids}`; сервер обрабатывает повтор идемпотентно                                                                                                                   | `job.event`, `job.complete`, `job.fail`, `job.reject`, `cmd.done`, `state.applied` |
| **запрос**   | ответ или ошибка                           | `id` → ответ с `re`; таймаут на стороне агента (30 с), повтор — новым запросом                                                                                                                          | `job.urls`                                                                         |

- `ack` сервера: `{ "ids": [..], "seq": N }`. `ids` — надёжные сообщения, обработанные
  окончательно, **в том числе отклонённые без повтора**; `seq` — последний принятый
  номер потока.
- Ошибка обработки — `error{re, code, message, retryable}`. `retryable: false` — агент
  удаляет сообщение из outbox и пишет в лог (например, `JOB_LEASE_LOST`: задачу уже
  забрали). `retryable: true` — сообщение остаётся в outbox и досылается с backoff.

## 5. Идентичность агента

1. Администратор выпускает **токен регистрации** (`POST /api/v1/agent-link/enrollment-tokens`):
   срок, число использований (парк машин), метки, признак `ephemeral`.
2. Агент при первом старте регистрируется:
   ```
   POST /api/v1/agent-link/enroll
   { "token": "…", "name": "gpu-01", "labels": {…}, "host": {…} }
   → 201 { "agentId": "…", "secret": "…" }
   ```
3. Учётные данные `agentId.secret` агент хранит в файле с правами `0600` в каталоге
   данных; дальше токен регистрации не нужен. Сервер хранит только sha256 секрета.
4. Отзыв агента (`POST /api/v1/agents/{id}/revoke`) закрывает его сессию кодом 4401.
   Агент с `ephemeral`-токеном (реплики без постоянного тома) регистрируется заново;
   остальные ждут с backoff и пишут в лог.

## 6. Сообщения

Обозначения: **A→S** — агент серверу, **S→A** — сервер агенту.

### 6.1 Сессия

**`hello`** (A→S)

```jsonc
{
  "protocols": [1],
  "agent": {
    "name": "gpu-01",
    "version": "1.0.0",
    "sdk": "go/1.0.0",
    "codeHash": "sha256…", // хеш исполняемого файла (необязательно)
    "bootId": "a1b2c3d4", // случайный id запуска процесса: начало нумерации seq
    "startedAt": 1791380000000,
  },
  "host": {
    "hostname": "gpu-01",
    "os": "linux",
    "arch": "amd64",
    "platform": "ubuntu 24.04",
    "kernel": "6.8.0",
    "cpus": 16,
    "memoryBytes": 68719476736,
  },
  "labels": { "zone": "eu" },
  "capabilities": {
    "jobs": { "queues": [{ "name": "demo.echo", "concurrency": 2 }] },
    "commands": { "names": ["agent.logs", "agent.drain", "agent.update"] },
    "state": { "domains": { "wg": 12 } }, // домен → применённая версия (null — нет)
    "telemetry": { "channels": ["host", "gpu"] },
    "update": { "mode": "self" }, // self | external | disabled
  },
  "jobs": [{ "jobId": "…", "attempt": 0 }], // держит: выполняются или итог ещё в outbox
}
```

**`welcome`** (S→A)

```json
{
  "protocol": 1,
  "agentId": "…",
  "sessionId": "…",
  "serverTime": 1791380000123,
  "config": { "statusIntervalMs": 15000, "metricsIntervalMs": 15000 }
}
```

**`config`** (S→A) — частичное обновление `welcome.config`.

**`ack`** (S→A) — `{ "ids"?: string[], "seq"?: integer }`.

**`error`** (S→A) — `{ "code": "…", "message": "…", "retryable": boolean }`, `re` — id
сообщения агента (если ошибка про конкретное сообщение).

### 6.2 Состояние и телеметрия

**`status`** (A→S, поток) — при каждом изменении и не реже `statusIntervalMs`. Это и
прикладной пульс: им сервер продлевает аренды всех перечисленных задач (§6.3).

```jsonc
{
  "state": "idle", // starting | idle | busy | draining | updating | degraded
  "message": "…", // причина degraded и т. п.
  "slots": { "demo.echo": 1 }, // свободные места по очередям
  "capacity": { "demo.echo": 2 }, // ёмкость очередей (нагрузки меняются после hello)
  "jobs": [
    {
      "jobId": "…",
      "attempt": 0,
      "queue": "demo.echo",
      "startedAt": 1791380000000,
    },
  ],
  "workloads": [
    { "name": "echo", "state": "running", "instances": 1, "version": "2.0.0" },
  ],
  "outbox": 0, // неподтверждённых надёжных сообщений
}
```

**`metrics`** (A→S, поток) — раз в `metricsIntervalMs`.

```jsonc
{
  "collectedAt": 1791380000000,
  "host": {
    "cpuPercent": 12.5, "load1": 0.4, "memUsedBytes": 1, "memTotalBytes": 2,
    "diskUsedBytes": 1, "diskTotalBytes": 2, "netRxBps": 100, "netTxBps": 100, "uptimeSec": 3600,
  },
  "gpus": [{ "index": 0, "name": "RTX 4090", "utilPercent": 97, "memUsedBytes": 1, "memTotalBytes": 2, "temperatureC": 71 }],
  "channels": { "wg": { … } }, // прикладные каналы телеметрии, схема — у потребителя канала
}
```

### 6.3 Задачи (`capabilities.jobs`)

Сервер раздаёт задачи сам (push) по свободным слотам из `status.slots`: это
источник правды об очередях агента (нагрузки регистрируются и перезапускаются
после `hello`); `hello.capabilities.jobs` объявляет возможность и очереди на момент
подключения. Агент шлёт `status` сразу при изменении слотов. Задача
выполняется под **арендой**: сервер продлевает её до `now + leaseSeconds` каждым
`status`, в котором задача перечислена. Пока агент без связи, аренда не продлевается;
вернулся раньше её истечения — задача продолжается, позже — задачу уже забрали
(повтор на другом агенте), и итог старой попытки отклоняется (`JOB_LEASE_LOST`).
Срок аренды — свойство очереди: для долгих задач он и есть допустимое время без связи.

**Сверка при `hello`:** задачи, которые сервер считает выполняющимися на агенте:

- агент их перечислил — продолжаются;
- агент их не перечислил и не подтверждал (`job.accept`) — `job.assign` повторяется;
- агент их не перечислил, но подтверждал — потеряны (рестарт агента): попытка
  проваливается с `AGENT_LOST`, повтор по политике очереди.

Задачи из `hello.jobs`, которые на сервере уже не выполняются на этом агенте, получают
`job.cancel`.

| Сообщение      | Направление            | data                                                                                                                                   |
| -------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `job.assign`   | S→A                    | `{jobId, attempt, queue, data, leaseSeconds, inputs: {имя: url}, outputs: {имя: {url, contentType?}}, urlsExpireAt?}`                  |
| `job.accept`   | A→S поток              | `{jobId, attempt}` — задача принята исполнителем                                                                                       |
| `job.reject`   | A→S надёжный           | `{jobId, attempt, code, message}` — не может выполнить (очередь не обслуживается, нет места); попытка возвращается в очередь           |
| `job.progress` | A→S поток              | `{jobId, attempt, progress?: 0..1, text?: ≤200, log?: string[] (≤100 строк ≤1000)}` — агент схлопывает частые обновления               |
| `job.event`    | A→S надёжный           | `{jobId, attempt, seq, type: ≤50, data?}` — доменное событие (метрики эпохи); `seq` с 1 в пределах попытки, сервер отбрасывает повторы |
| `job.urls`     | A→S запрос / S→A ответ | запрос `{jobId, attempt, inputs?: string[], outputs?: string[]}` → ответ `{inputs, outputs, expiresAt}` — свежие подписанные ссылки    |
| `job.cancel`   | S→A                    | `{jobId, attempt}` — прервать немедленно, итог не отправлять                                                                           |
| `job.stop`     | S→A                    | `{jobId, attempt}` — штатная досрочная остановка: довести шаг и сдать `job.complete`                                                   |
| `job.complete` | A→S надёжный           | `{jobId, attempt, result?}`                                                                                                            |
| `job.fail`     | A→S надёжный           | `{jobId, attempt, code: ^[A-Z0-9_]+$ ≤64, message: ≤2000, retryable}`                                                                  |

Коды ошибок задачи, которые выставляет сам агент: `WORKER_ERROR` (исключение
обработчика), `WORKLOAD_CRASHED` (процесс нагрузки упал), `QUEUE_NOT_SERVED`,
`UPLOAD_FAILED`.

### 6.4 Команды (`capabilities.commands`)

Команды — белый список имён, объявленный агентом. Сервер доставляет команды в статусе
`pending` (повторно — после переподключения, агент дедуплицирует по `commandId`).

| Сообщение    | Направление  | data                                                           |
| ------------ | ------------ | -------------------------------------------------------------- |
| `cmd.run`    | S→A          | `{commandId, name, args?, timeoutSec}`                         |
| `cmd.accept` | A→S поток    | `{commandId}`                                                  |
| `cmd.output` | A→S поток    | `{commandId, chunk: ≤64 КБ}`                                   |
| `cmd.done`   | A→S надёжный | `{commandId, ok, exitCode?, result?, error?: {code, message}}` |

Встроенные команды агента:

| Имя                | args                                | Что делает                                                             |
| ------------------ | ----------------------------------- | ---------------------------------------------------------------------- |
| `agent.logs`       | `{lines?: ≤5000}`                   | хвост собственного лога агента и нагрузок                              |
| `agent.drain`      | —                                   | перестать брать задачи, текущие доработать (`status.state = draining`) |
| `agent.resume`     | —                                   | снова брать задачи                                                     |
| `agent.restart`    | —                                   | перезапуск процесса агента (после доработки задач)                     |
| `agent.update`     | `{version, url, sha256, signature}` | самообновление исполняемого файла (§7)                                 |
| `workload.restart` | `{name}`                            | перезапуск нагрузки без простоя: новый экземпляр, старый дорабатывает  |

### 6.5 Желаемое состояние (`capabilities.state`)

Домен (например, `wg`) — полный снимок с монотонной версией. Агент сохраняет снимок на
диск, применяет идемпотентно, при ошибке повторяет, после рестарта применяет из кэша
без сервера.

| Сообщение       | Направление  | data                                                               |
| --------------- | ------------ | ------------------------------------------------------------------ |
| `state.put`     | S→A          | `{domain, version, spec}`                                          |
| `state.applied` | A→S надёжный | `{domain, version, ok, error?, report?}` — `report` — схема домена |

Сервер отправляет `state.put`, если версия домена новее применённой агентом
(`hello.capabilities.state.domains` и последнего `state.applied`). Агент применяет
только версию новее применённой; пришедшие подряд снимки схлопываются до последнего.

## 7. Обновление агента

- **Исполняемый файл** (`update.mode = self`, systemd): команда `agent.update` →
  скачать во временный файл → сверить sha256 → проверить подпись **Ed25519** ключом
  выпуска, вшитым в агент или заданным в конфигурации → сохранить текущий как `.prev` →
  атомарно заменить → перезапуск. Новая версия, не дошедшая до `welcome` за 3 запуска,
  откатывается на `.prev`.
- **Контейнер** (`update.mode = external`): агент только сообщает версию; обновление —
  новым образом через оркестратор.
- **Нагрузки** — `workload.restart`: новый экземпляр поднимается рядом, старый перестаёт
  брать задачи и завершается после текущих.

## 8. Совместимость

- Внутри версии протокола изменения только **добавляются**: новые необязательные поля,
  новые типы сообщений, новые возможности. Получатель игнорирует незнакомое.
- Несовместимое изменение — новая версия протокола. Сервер поддерживает текущую и
  предыдущую; агент объявляет все, которые знает.
- Новая возможность объявляется в `hello.capabilities`; сервер не шлёт агенту сообщения
  возможности, которую тот не объявил.

## 9. Эталонные сообщения

[`fixtures/`](fixtures) — по файлу на тип сообщения (`<type>.json`, варианты —
`<type>.<вариант>.json`): конверт целиком; `a2s/` — агент → сервер, `s2a/` — сервер →
агент. Тесты реализаций:

- сервер принимает каждое сообщение `a2s/` своей схемой валидации;
- агент разбирает каждое сообщение `s2a/` и `a2s/` и сериализует обратно без потери полей.

## 10. Локальный протокол нагрузок

Нагрузка (workload) — дочерний процесс агента, выполняющий задачи (Python-воркер,
любой язык). Агент запускает её по конфигурации и держит с ней канал IPC:
**unix socketpair, унаследованный дескриптор `ALP_IPC_FD` (3)**, по строке JSON на
конверт (§4). Сеть, переподключение, outbox, учётные данные и обновление — забота
агента; нагрузка знает только задачи.

Окружение нагрузки: `ALP_IPC_FD`, `ALP_WORKLOAD` (имя), `ALP_AGENT_VERSION`.

| Сообщение           | Направление | data                                                                               |
| ------------------- | ----------- | ---------------------------------------------------------------------------------- |
| `workload.register` | W→A         | `{name, version, sdk, queues: [{name, concurrency}]}` — первое сообщение, за 120 с |
| `workload.ready`    | A→W         | `{agentVersion}` — регистрация принята                                             |
| `workload.drain`    | A→W         | `{}` — не брать новых задач, завершиться после текущих (перезапуск без простоя)    |
| `job.assign`        | A→W         | как в §6.3                                                                         |
| `job.cancel`        | A→W         | как в §6.3 — прервать, итог не отправлять                                          |
| `job.stop`          | A→W         | как в §6.3 — довести шаг и сдать `job.complete`                                    |
| `job.progress`      | W→A         | как в §6.3                                                                         |
| `job.event`         | W→A         | как в §6.3; `seq` нумерует нагрузка (с 1 в пределах попытки)                       |
| `job.urls`          | W→A запрос  | как в §6.3, с `id`; ответ агента — `job.urls` или `error` с `re`                   |
| `job.complete`      | W→A         | как в §6.3                                                                         |
| `job.fail`          | W→A         | как в §6.3                                                                         |

- **Остановка** — `SIGTERM`: нагрузка перестаёт брать задачи, дорабатывает текущие и
  завершается; через `stopTimeout` агент шлёт `SIGKILL`.
- **Падение** нагрузки — её задачи проваливаются с `WORKLOAD_CRASHED` (с повтором), агент
  перезапускает процесс с backoff.
- Нагрузка вправе печатать в stdout/stderr — агент пишет это в свой лог с её именем.
