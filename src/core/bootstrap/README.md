# bootstrap

Контракт бутстраперов: задач старта (сиды, запуск очереди, сокет-сервер) и их
остановки. Сам каталог ничего не запускает — только описывает интерфейс и токен.

## Public API

| Экспорт      | Что                                                                    |
| ------------ | ---------------------------------------------------------------------- |
| `IBootstrap` | `initialize()`, необязательный `destroy()`, необязательный `critical`  |
| `BOOTSTRAP`  | DI-токен multi-inject, под которым `ModuleLoader` собирает бутстраперы |

## Устройство

- Модуль объявляет класс в `@Module({ bootstrappers: [...] })`; `ModuleLoader`
  привязывает его под `BOOTSTRAP` (singleton). Если тот же класс уже есть в
  `providers`, под `BOOTSTRAP` резолвится **тот же экземпляр** — сервис с
  состоянием можно инжектить и как бутстрапер.
- `App` вызывает `initialize()` последовательно в порядке загрузки модулей (импорты —
  раньше импортёра), после миграций и регистрации маршрутов. `destroy()` — при
  остановке, в обратном порядке.
- `critical` по умолчанию истина: сбой прерывает запуск. `critical = false` — сбой
  только логируется (сиды, некритичные фоновые задачи).

## Зависимости

Зависимостей нет. Использует `src/app.ts` и `core/module-loader.ts`; реализации — в
модулях user (`AdminBootstrap`, `SeedBootstrap`), jobs (`JobsBootstrap`), socket
(`SocketBootstrap`).

## Gotcha

- Процесс-воркер (`APP_ROLE=worker`) тоже запускает все бутстраперы — роль процесса
  бутстрапер проверяет сам.
- `/ready` отвечает 200 только после завершения всех `initialize()`.
